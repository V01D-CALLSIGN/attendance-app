# Attendance App — Product and Technical Decisions

## Repository inspection

The repository began as the default SwiftUI application generated by Xcode 26.6. It contained one app target, `attendance-app`, one placeholder `ContentView`, no tests, packages, persistence, or established design system. Phase 1 therefore uses native SwiftUI only and keeps dependencies at zero.

## Information architecture

The product has two modes:

1. **Setup** — a short guided flow: Welcome → Classes → Students → Assignments → Review.
2. **Daily work** — Home-first operation: next class → roster → attendance, with Calendar, Students, Reports, and Settings as secondary destinations.

The hierarchy is deliberately class/session-first rather than student-first. The instructor's most frequent task begins with the next scheduled class. Students are shared records and can be assigned to any number of classes. Makeup eligibility is contextual information shown while adding someone to a makeup session.

## Navigation

- `RootView`
  - `OnboardingFlow` when setup is incomplete
    - Welcome
    - Class setup and weekly preview
    - Student setup
    - Multi-class assignment
    - Setup review
  - `MainTabView` after setup
    - Home: next class, remaining schedule, alerts, summary
    - Calendar: weekly class schedule
    - Students: searchable directory and creation
    - Reports: Phase 1 local summary
    - Settings: prototype controls and scope disclosure
  - Class cards navigate to `ClassRosterView`
  - `ClassRosterView` presents attendance entry and the Add Student picker

## Data model

- `Student`: stable ID, first/last name, grade, optional contact and notes.
- `ClassCourse`: stable ID, name, weekday, start/end minutes, recurrence, dates, location, color token, and `isMakeupClass`.
- `Enrollment`: many-to-many link between student and class with an effective date and optional end date.
- `ClassSession`: one dated occurrence of a class; separates a recurring definition from attendance.
- `AttendanceRecord`: session/student status, notes, and optional late arrival.
- `MakeupCredit`: student, originating missed session, lifecycle state (`owed`, `scheduled`, `completed`, `waived`, `expired`), optional scheduled session, and expiry.

Relationships:

```text
Student ──< Enrollment >── ClassCourse ──< ClassSession ──< AttendanceRecord
   │                                                │
   └──────────────────< MakeupCredit >──────────────┘
```

All views depend on the `AttendanceRepository` protocol. `LocalAttendanceRepository` owns Phase 1 on-device persistence and mutations. A later `SupabaseAttendanceRepository` can implement the same boundary, while local models can become DTO/domain mappings without changing view intent.

## Implementation phases

### Phase 1 — local functional prototype (this build)

- Guided onboarding and review.
- Create classes and students.
- Assign students to multiple classes.
- Home dashboard and weekly calendar.
- Searchable class roster and add-student flow.
- Attendance statuses, mark-all-present, undo, notes, and save.
- Makeup search across the entire student database with visible credit state.
- Blank first-run state with user-created data persisted as an atomic Codable snapshot in Application Support.
- Development-only confirmed reset that deletes the local snapshot and resets onboarding.
- Monday-to-Sunday conversational class setup with Art/Study selection, time confirmation, same-day repeats, and weekly review.
- Monthly student reports derived from enrollment-effective recurring sessions, with enrollment and session snapshots protecting historical class labels and times.

### Phase 2 — durable single-user product

- Supabase schema and repository adapter, migrations, offline cache/sync policy.
- Authentication and account recovery.
- Durable recurrence expansion, timezone handling, photos, bulk import, editing, and deletion safeguards.
- Full makeup-credit creation, expiry policy, audit trail, and conflict handling.

### Phase 3 — connected operations

- Google Calendar synchronization with conflict/source-of-truth rules.
- Messaging and contact workflows.
- Production reports/export, roles, observability, accessibility audit, and payments if required.

## Important assumptions

- Phase 1 targets portrait iPhone first; layouts remain usable on iPad, but tablet drag-and-drop is deferred. Tap-and-check assignment is the reliable phone interaction.
- The weekly preview uses Monday–Friday and a practical afternoon/evening window for tutoring. Data still supports all weekdays.
- A class definition is recurring; attendance belongs to dated sessions. Phase 1 creates sessions on demand.
- Adding a student to a normal roster creates an ongoing enrollment from today. The requested today-only/chosen-date prompt is represented in the model but its full scheduling UI is deferred.
- Adding to a makeup class is session-only. It never creates recurring enrollment in Phase 1.
- Saving a makeup attendee with an eligible scheduled credit completes that credit; completed credits cannot be selected again.
- No authentication, payments, messaging, external calendar integration, remote API, analytics SDK, or production backend is included.
- A clean installation contains no classes, students, enrollments, sessions, attendance, makeup credits, or derived report statistics.
